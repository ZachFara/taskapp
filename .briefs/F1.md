# F1 Undo and redo   (ID: F1, migration: 0002_undo.sql)

Goal: every change can be undone and redone as ONE step, including bulk edits and agent (MCP/CLI) edits. Built on the `changes` table.

- Group changes into steps: add a step id (and a label, e.g. "Set status on 3 issues") to `changes`; every command call
  that writes is one step, however many rows and entities it touches. A bulk command over N issues is one step.
- `undo()` reverts the newest not-undone step by applying old values in reverse order; `redo()` reapplies it. A new
  change after an undo clears the redo stack. Undo/redo themselves are recorded with a distinct ChangeSource so
  history stays truthful, and they never become undoable steps of their own in a way that loops.
- Cover creates and deletes too (undo of create = delete or archive, undo of delete = restore with the same id and
  links). If a kind of change cannot be undone safely (e.g. a deleted status that issues were moved off), undo must
  refuse with a clear error, not half-apply. List every such case in the report.
- Conflicts: if the current value no longer equals the step's new value (something else changed it since), refuse that
  step with an error naming the field; do not overwrite.
- Expose: core `undo`, `redo`, `undo_status` (labels of next undo and redo steps); commands dispatch; Tauri; MCP tools;
  CLI `undo` / `redo`; mock api.
- Tests: single edit; bulk edit as one step; create; delete+restore; redo; redo cleared by new change; conflict refusal;
  an edit made through the MCP path is undoable.
- Sync side effects (gcal, reminders, export) are out of scope: undo changes the db only; say so in the report.
