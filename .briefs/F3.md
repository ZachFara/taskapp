# F3 Icons and colors   (ID: F3, migration: 0004_icons.sql)

Goal: projects, views, labels, statuses and cycles each carry an icon and a color. (Issue templates get the same two
columns in their own task; do not touch templates.)

- Migration adds `icon TEXT NULL` to projects, views, labels, statuses, cycles, and `color TEXT NULL` where the table
  has no color column yet. Existing color columns keep working.
- Icon value: either `"icon:<id>"` (an id from one icon set, chosen later: validate only the shape `[a-z0-9-]{1,40}`)
  or `"emoji:<one emoji grapheme>"`. Reject anything else.
- Color value: a palette key, not a hex. Define the palette as one Rust const list of 12 keys
  (gray, red, orange, amber, yellow, green, teal, cyan, blue, indigo, purple, pink) in one place, exported to the UI
  bindings. The design round picks the actual hex values per theme later. Migration maps existing hex colors to the
  nearest key; keep a test for the mapping.
- Add the fields to the model structs, the read queries, and the create/update commands of those five entities; changes are recorded in history.
- Expose through existing commands (extended args), MCP tools, CLI flags `--icon`, `--color`, mock api and bindings.
- Tests: set/get per entity; shape validation; unknown color key rejected; migration maps old hex colors; history rows written.
- Existing UI code reads `color` as hex in places: do NOT edit components. If a type change breaks the UI build or UI
  tests, keep the old hex field readable (e.g. also return a resolved default hex) and say exactly what you did.
