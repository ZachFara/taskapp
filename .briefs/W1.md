Owner's words: "make sure we have options for what to display on each view ... what properties or metadata to display within each view. In addition we should have the ability to make view templates where other views start from too. We should be able to also display the additional custom metadata."
Cargo allowed (`-j 4`). Read .briefs/F-common.md (sqlx, migrations: use 0009_view_templates.sql) and .briefs/I-common.md.
Owns: crates/core/src/views.rs and the view parts of model.rs, the views commands in crates/commands, mcp and cli view tools, ui/src/lib/api.mock*.ts + ui/src/lib/contract/** (view cases only), ui/src/lib/bindings.ts (generated), ui/src/components/ViewEditor.svelte, ui/src/app/ViewPage.svelte, ui/src/components/views/** (all five layouts), ui/src/components/ViewsPage.svelte, ui/src/components/display/** (new), ui/src/lib/commands/defs/view/**.

## A. Display options (per saved view, per layout)
- `ViewDef.columns: Vec<FieldRef>` already exists and only the Table uses it. Make it the view's ordered list of DISPLAYED FIELDS for every layout. A FieldRef can be a built-in field (key, priority, status, title is always shown, labels, project, milestone, cycle, parent, start, due, estimate, created, updated, sub-issue progress, relation count, comment count) or ANY custom property definition (text, number, date, select, checkbox, url ...). Add what is missing to FieldRef/the query so each of those can be returned and shown; empty `columns` means the layout's default set (keep today's look as the default).
- Add per-view display settings to ViewDef (backwards compatible with stored JSON: `#[serde(default)]`): `density` (comfortable | compact), `show_empty_groups`, `show_sub_issues` (nest | flat | hide), `card_fields` used by the board when set (else `columns`), `show_weekends` (timeline/calendar). Stored with the view, round-tripped by core, commands, MCP, CLI, mock, bindings, contract cases.
- UI: the "Display" popover becomes a real panel (new `components/display/DisplayPanel.svelte`): a searchable list of every built-in field and every custom property with a Switch each, drag (and keyboard: alt+up/down commands) to reorder, a "Reset to default" action, the density and grouping-related switches, and layout-specific options shown only for the current layout. Changes apply live and save to the view (debounced, one undo step per change).
- Every layout honours it:
  - List: the row's metadata columns are exactly the displayed fields in order (title flexes; others size by type; numbers and dates right-aligned; a custom select property renders as a Pill in its option colour, checkbox as a glyph, url as a link icon, date as a human date, number with tabular figures). Compact density uses the compact row height token.
  - Board: cards show the displayed fields (key and title always; others as a compact metadata line/chips), so custom properties can appear on cards.
  - Table: columns = displayed fields (existing behaviour), plus the same renderers; header "+" adds a field through the same panel.
  - Timeline: left-pane columns after the title come from the displayed fields (first 3 that fit), bar label optional field.
  - Calendar: chip shows title plus up to 2 displayed fields (e.g. priority glyph, project icon).
  One shared renderer `components/display/FieldValue.svelte` used by all five so a custom property looks the same everywhere.
- Grouping and sorting by a custom property must work in list, board (select and checkbox properties give columns) and table: check, fix, test.

## B. View templates
- A view template is a saved view definition that new views start from. Backend: `views.is_template` (migration 0009) or a `view_templates` table (your call; say why), with name, icon, colour and a full ViewDef (filter, sorts, group, layout, displayed fields, display settings). Commands: list/create/update/delete template, `views_create_from_template(template_id, name?)` (one history step), `views_save_as_template(view_id, name?)`, and a workspace setting `default_view_template` that "New view" uses when set. Undo/redo covers all of them (row changes like other entities). Expose via dispatch/Tauri/MCP/CLI, mock, bindings, contract cases.
- Seed three neutral templates in the dev seed AND the mock (kept identical): "Status board" (board by status, card fields priority, labels, due), "Planning table" (table with priority, status, project, estimate, due + every custom property), "This week" (list, due within 7 days, grouped by project). First-run workspaces get the same three.
- UI: Views page gets a "Templates" section (ListRow list with icon, name, layout; rename, edit, delete with confirm Dialog, "Set as default"); "New view" opens a small Dialog: "Start from" = Blank, any template, or "Copy of current view"; the view header's "..." menu gains "Save as template" and "Reset to template" (when the view came from one: store `template_id` on the view). Commands for all of it in defs/view/ (view.new already exists: make it open this dialog), each with label, icon, shortcut or reason.
