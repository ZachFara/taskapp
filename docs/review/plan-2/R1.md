## Findings

### R1-1 Important: view template keeps a deleted custom property; views made from it cannot be queried
- where: crates/core/src/properties.rs:443 (`strip_from_views` only scrubs `views`), crates/core/src/view_templates.rs (create_view, reset_view)
- what: deleting a property removes it from every saved view but not from view templates. "New view from template" and "Reset to template" then produce a view whose filter/sort names a property that no longer exists; `views::query` returns `Invalid("unknown property")` every time, so the view is permanently broken until its filter is edited by hand (if the UI even lets it load).
- repro: `cargo test -p taskapp-core --test r1_probe p1 -- --nocapture`. Creates property `area`, template with filter+sort on it, `delete_def("area")`, template def still holds `{"Property":"area"}`, `create_view` then `views::query` gives `Err(Invalid("unknown property"))`.
- fix: run the same strip over `view_templates` in `delete_def` (and snapshot the table so undo restores it).

### R1-2 Minor: `settings_set` command writes any key unvalidated (bypasses workspace_setup rules)
- where: crates/commands/src/lib.rs:246 `settings_set`; crates/core/src/settings.rs:19
- what: the UI/IPC can set `issue_prefix` to `"bad key!"` or `timezone` to `"Mars/Base"`; `workspace::status` then reports them as is. validate_key and the zone check only run in `workspace::setup`.
- repro: `cargo test -p taskapp-core --test r1_probe p2 -- --nocapture` prints `key: "bad key!"` and `timezone: "Mars/Base"`.
- fix: validate `issue_prefix`/`timezone`/`setup_done` inside `settings::set`, or reject those keys in the command.

### R1-3 Minor: statuses::delete lets the last status of a category be deleted
- where: crates/core/src/statuses.rs `delete`
- what: deleting `Done` (only Completed status) moving issues to Backlog leaves 0 Completed statuses and the moved issue keeps `completed_at` (the latter is a documented shortcut). No UI path calls it yet, but the contract case exists.
- repro: `r1_probe p6` prints `completed statuses left: 0` and `completed_at Some(..)` on an issue now in Backlog.
- fix: refuse when it is the last status of its category (or when the target category differs, clear completed_at).

### R1-4 Minor: key lookup accepts forms the display never produces
- where: crates/core/src/issues.rs:540 `get_by_key`
- what: `ABC-+1` and `ABC-01` resolve to issue 1 (i64 parse); lowercase `abc-1` and surrounding spaces do not resolve. Prefix is otherwise ignored as designed (`ZZ-1` resolves; works after a prefix change).
- repro: `r1_probe p3`.
- fix: parse digits only (`n.bytes().all(is_ascii_digit)`), and upper-case/trim the input.

### R1-5 Minor: a non-step change (Agent or Cli write outside `history::step`) leaves a stale "redo" offered
- where: crates/core/src/history.rs `current_step`
- what: such a write has no step, so it does not clear the redo stack; redo then refuses with a Conflict naming the field. Safe (nothing applied), just confusing. MCP and CLI do wrap calls in a step, so only direct library callers hit it.
- repro: `r1_probe p5`: undo, then an Agent-source update outside a step, then `redo` gives `Conflict("priority of ABC-1 changed since this step")`.
- fix: none needed unless a writer outside step is added; consider a debug assert in `record`.

### R1-6 Important: no test for undo refusing a step with an uncovered entity
- where: crates/core/src/undo.rs `covered` / check in `run`
- what: disabling the refusal changes no test result, so the "applied whole or not at all" guarantee for unknown entities is untested.
- repro: mutation above. fix: a test that inserts a change row with an unknown entity into a step and asserts undo returns Invalid and changes nothing.

### R1-7 Important: no test that a failing issue update inside a bulk edit rolls everything back
- where: crates/core/tests/bulk.rs `a_failing_item_applies_nothing`
- what: that test fails only through the self-relation (`add_in`) path. Swallowing the error from `issues::update_in` (e.g. an invalid patch on the second issue) leaves the first issue edited and no test fails.
- repro: mutation above (`let _ = issues::update_in(...)`), `cargo test -p taskapp-core --test bulk`. fix: add a case where the second id is unknown or the patch invalid, assert the first is unchanged.

- fix: test a def with a quote in its key, or confirm create_def forbids it and drop the guard.
