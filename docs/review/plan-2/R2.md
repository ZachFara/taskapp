# R2 review: agents and data in/out (origin/plan-2 @ 2f25faa, worktree ../taskapp-wt/R2)

## Findings

### R2-1  Important (data loss on restore)  Export/rebuild drops icons, colours, issue templates, view templates
where: crates/export/src/write.rs (queries at :127,:135,:143,:181,:199), crates/export/src/files.rs (StatusRow, LabelRow, CycleRow, ProjectFile, ViewFile), crates/export/src/rebuild.rs
what: the export writes no `issue_templates` or `view_templates` at all, and omits `icon` (statuses, labels, projects, cycles, views), `color` (projects, cycles, views) and `views.template_id`. A rebuild from an export gives back a database without them. View display settings (density, show_weekends) DO survive. `import_log` is not exported either, so after a rebuild a CSV/Linear re-import duplicates everything.
repro: throwaway test crates/export/tests/r2_probe.rs (in worktree, uncommitted): insert via SQL a status icon, label icon+colour, project icon+colour, cycle icon+colour, a view with icon/colour/template_id/density, an issue_template, a view_template; `write::write_snapshot` to a temp dir, `rebuild::rebuild` to a new db, select the same columns. Run `cargo test -p taskapp-export --test r2_probe -- --nocapture`. Output: every icon/colour is `-`, issue_templates `[]`, view_templates `[]`, view template_id `-`; the exported dir has only settings, views, labels, properties, projects/, statuses, cycles, pins (no templates files).
why no test noticed: tests/export.rs `rebuild_roundtrip` compares export-of-export with export, so anything the writer never writes cannot differ.
fix: add icon/color/template_id fields and templates.yaml / view_templates.yaml to files.rs, write.rs and rebuild.rs; extend the round-trip test to start from a db with every plan-2 column filled and compare table dumps, not trees.

### R2-2  Important  Undone CSV import cannot be re-imported ("already imported")
where: crates/core/src/import_plan.rs `skip_imported` / undo.rs (undo archives issues, `import_log` rows stay)
what: after `undo` of an import the 5 issues are archived but still in import_log, so a new dry run says every row "already imported" and apply creates nothing; the only way back is redo.
repro: `taskapp --db a.db setup Test TST --tz Europe/London; taskapp --db a.db import csv f.csv --apply; taskapp --db a.db undo; taskapp --db a.db import csv f.csv` -> skipped: 5 x "already imported"; sqlite `select count(*), sum(archived_at is null) from issues` = 5|0, import_log = 5.
fix: treat an import_log row whose issue is archived (or deleted by undo) as not imported, or have undo delete the log rows (undo of `import_log` rows is not recorded).

### R2-3  Important  Import writes hex colours; the next db open rewrites them, so undo of any import that creates a label is refused
where: crates/core/src/import_plan.rs:12 (`COLOR = "#95a2b3"`, used for labels at ensure_refs and statuses), crates/core/src/palette.rs:112 `map_legacy_colors` (runs on open)
what: new labels and statuses get the raw hex, not a palette key (palette keys are the only valid colour elsewhere: `labels_create` with `teal2` is Invalid). The row snapshot recorded for undo holds the hex; the next `Db::open` rewrites it to `gray`, so undo says `conflict: labels 7 changed since this step`. Every CLI call is a new process, so `taskapp import csv X --apply` then `taskapp undo` always fails; in the app it fails after a restart. The devserver also returns the status "Waiting" with colour `#95a2b3` (see contract probe below), a value the UI never otherwise sees.
repro: `taskapp-devserver seed --db u.db; printf 'title,labels\nX,newlab\n' > l.csv; taskapp --db u.db import csv l.csv --apply; sqlite3 u.db "select color from labels where name='newlab'"` -> `#95a2b3`; `taskapp --db u.db undo` -> `error: conflict: labels 7 changed since this step`; afterwards colour is `gray`. 50k-row import (labels l0..l6): apply 40 s, undo takes 44 s and then fails the same way.
fix: use the palette key `gray` for new labels/statuses (and the select options inferred in import_csv.rs `infer`); make the conflict message name the cause.

### R2-4  Important  Mock redo of a created issue leaves it archived; the contract case that should catch it checks the wrong issue
where: ui/src/lib/api.mock.ts:124-131 (`undoRedo` iterates `from_ = st.before` on redo, which does not contain the created issue); ui/src/lib/contract/cases.ts cases 'undo: the issue is gone' / 'undo: the issue is back' use key `ABC-25`, but the issue "Undo me" is ABC-32 (ABC-25 is the earlier quick-add issue, so both cases compare an unrelated, untouched issue).
what: this is the reported divergence. After the whole table, an unfiltered `views_query` has 32 rows in the mock and 33 in the real backend; the missing one is WRK-32 "Undo me" (archived_at set in the mock, null in the real one). Redo of an issue creation therefore does nothing in the mock (UI dev mode/demo), and the contract is blind to it.
repro: throwaway ui/src/lib/contract/r2bisect.test.ts runs the table prefix by prefix plus `issues_get_by_key ABC-32` on both sides. Output: `after case #126 "undo: undo": mock archived=yes | real archived=yes`, then `after case #128 "undo: redo": mock exists archived=yes | real exists archived=no`. (`pnpm -C ui exec vitest run src/lib/contract/r2bisect.test.ts --silent=false`; needs `cargo build -p taskapp-devserver`.)
fix: on redo also walk `to` (the after list) so an id missing from `before` is restored; point the two cases at the key returned by 'undo: create an issue' (ABC-32) and add an unfiltered `views_query` after the duplicate and undo cases.

### R2-5  Important  Silent no-op success: MCP ignores unknown argument names
where: crates/mcp/src/tools.rs `create_issue` (serde_json::from_value(a.clone())) and `update_issue` (`arg::<IssuePatch>`): neither type rejects unknown fields
what: `update_issue {"key":"ABC-1","patch":{"bogus":1}}` returns the unchanged issue as success; `create_issue {"title":"x","bogus":1}` succeeds. A typo like `prioriy` or `status` (instead of `status_id`) looks like it worked. Because writes are not applied, the agent only finds out by re-reading.
repro: throwaway crates/mcp/tests/r2_probe.rs `probe_a` (`cargo test -p taskapp-mcp --test r2_probe probe_a -- --nocapture`): A[2] and A[5] return Ok with the issue.
fix: `#[serde(deny_unknown_fields)]` on NewIssue/IssuePatch/TemplateInput (check the UI bindings still deserialize) or check keys in the tool layer.

### R2-6  Important  The MCP server states it never touches Linear, but `import_linear_plan` calls it
where: crates/mcp/src/main.rs:1 and :17 (get_info instructions "Never touches Linear or any other service"), tools.rs create_issue description ("Never reads or writes Linear"), vs tools.rs `import_linear_plan` -> core `CurlLinear` (curl to https://api.linear.app/graphql with $LINEAR_API_KEY)
repro (no network): put a fake `curl` first on PATH that logs its args and stdin, `LINEAR_API_KEY=SECRETTOKEN123`, call `import_linear_plan` via crates/mcp/tests/r2_probe.rs `probe_c_linear`: the fake curl was called with `--config -` and stdin `url = "https://api.linear.app/graphql"`, `header = "Authorization: SECRETTOKEN123"`. So the claim in the server's own instructions is false and an agent (or user reading them) is told no network access happens. Token handling itself held (see "Checked and fine").
fix: reword get_info/main.rs doc to "reads Linear only through import_linear_plan".

### R2-8  Minor  CSV edge cases give silent or confusing results
where: crates/core/src/import_csv.rs `parse`, `plan`, import_plan.rs `skip_imported`
- Duplicate header names (`title,title`): both columns map to title, the later wins, the first is dropped with no warning (`First` lost; repro `printf 'title,title,priority\nFirst,Second,high\n' | ...` plan shows only "Second", warnings []).
- Old-Mac CR-only line endings: `\r` is ignored outside quotes, so the whole file is one header row; plan has 0 issues and `unmapped: ["priorityOld Mac","highB","low"]`, no error.
- `skipped[].row` means the file row for "duplicate of an earlier row" but the index among remaining issues for "already imported" (re-plan of a 5-row file reports rows 1 to 5, offset by the header and dropped rows).
- No size cap: a 25 MB single cell and 50k rows are accepted (plan 2.3 s, apply 40 s); the MCP plan would return the whole JSON.
Fine: BOM, CRLF, `""` escapes, newline inside quotes, unterminated quote (clear error), empty file (clear error), bad dates (row skipped with reason), formula-looking cells (=, +, -, @) are stored verbatim.
fix: warn on duplicate headers and a headerless-looking single row; use the same row numbering in both reasons.

## Checked and fine
- Linear token: with a fake `curl` the token is on stdin only (never in args), and is replaced by `[token]` in the GraphQL error path and the non-JSON stderr path; Debug prints `Token(redacted)`; the db and its dump contain no token after an apply (grep count 0). Weak point only: a 1-character token mangles the message (`Lin[token]ar`), irrelevant in practice.
- CSV dry run writes nothing (issues and import_log counts 0 after plan); apply equals the plan shown; re-import skips everything ("already imported"); formula-leading cells are stored verbatim and the export is markdown/yaml only (no CSV export exists, so injection on export does not apply).
- devserver: foreign or portless Host -> 403; text/plain and form bodies -> 415; malformed or empty JSON -> 400; 5 MB body -> 413; GET -> 405; preflight allowed only for `--allow-origin`; the real-db guard holds for the exact path, a symlink, `..`, other case, and a relative path (tested with HOME pointed at a temp dir), and a sibling `taskapp2` is correctly allowed. The server does not check Origin on the actual POST (cross-site needs a preflight because of the JSON content type; preflight with a foreign Host still gets the allow header, though the following POST is 403). Defence in depth only.
- MCP: errors come back as tool errors; `bulk_update` is atomic and one undo step; workspace_setup validates key/zone and is idempotent (view templates not duplicated); `undo` from an agent works and records no step of its own.
- `import_apply` (MCP) with a plan of the wrong shape returns a clear Invalid error.
